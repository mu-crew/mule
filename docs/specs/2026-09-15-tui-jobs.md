# Interactive TUI jobs with durable mule state

Date: 2026-09-15
Status: proposed
Targets: mule 0.2.0; murmur 0.5.0 if unreleased, otherwise the next patch

Spans mule and murmur. mule owns the remote job, PTY, artifacts, and lifecycle.
murmur owns discovery, screen glance, and the peer-specific jump command. mu
continues to own only a local attach pane when an orchestrator needs control.

## Problem

A `pi-meta` process launched through mule now appears in murmur with the correct
private tmux server identity. Jumping reaches the correct pane but does not show
the pi TUI.

mule runs every command with stdout and stderr piped to its durable log:

```text
command -> log cap writer -> artifact
```

The pipe removes the command's direct connection to the pane PTY. A normal
`tee` cannot fix this: pi would still see a pipe rather than a terminal.

murmur glance has a second gap. Jump and liveness are server-aware, but glance
still runs plain `tmux capture-pane` on the default server. A private-server
pane therefore renders blank even when its TUI is healthy.

## User view

Launch an interactive agent:

```sh
id=$(mule run --tui 'pi-meta --pi-meta-no-solo --approve')
```

mule prints pasteable hints with real values:

```text
TUI job 3fa921 is interactive
  view current screen: mule tail 3fa921
  jump/interact:       murmur pick --all    # select mule-3fa921
  control through mu:  mu agent spawn mule-3fa921 --command \
    "$(murmur jump-command --host dev --agent mule-3fa921)"
  stop and remove:     mule kill --rm 3fa921
```

`--human` remains compatible with `--tui`; it opts out of crew metadata without
changing the PTY mode.

`--tui` conflicts with `run --wait` and `--no-tail`. A TUI agent may run for
hours, so blocking the local tool call recreates the failure mule removes. A
later explicit `mule wait <id>` remains available for callers that deliberately
want state-only waiting.

## mule execution

### Keep the process on the pane PTY

A TUI job executes its stored command file directly from the pane wrapper:

```sh
sh "$job_dir/cmd"
```

Do not decode the command through a pipe into `sh`; that would give the final
shell a pipe for stdin. The wrapper shell remains on the tmux pane PTY, so the
child inherits terminal stdin, stdout, and stderr.

Use `tmux wait-for` as a start barrier:

1. Write command and metadata artifacts.
2. Start the detached session. Its wrapper waits on a job-specific channel.
3. Install `tmux pipe-pane` on the target pane.
4. Signal the channel with `tmux wait-for -S`.
5. The wrapper runs the command on the PTY.

The barrier prevents early output from escaping before `pipe-pane` is active.
The channel uses only the validated job id.

### Copy output without stealing the PTY

`tmux pipe-pane` copies pane output to mule's log-cap writer:

```text
pi TUI <-> pane PTY <-> murmur attach
               |
               +-> pipe-pane -> capped transcript artifact
```

The copy includes terminal control sequences and redraws. Apply the existing
`max_log_bytes` cap to the pipe consumer. Reaching the cap stops transcript
capture but does not terminate or detach the TUI process. Record the existing
`truncated` marker.

On command exit:

1. Capture the visible pane with `tmux capture-pane -p -J` into a `screen`
   artifact while the wrapper still owns the pane.
2. Disable `pipe-pane`.
3. Write `rc` if no watchdog or kill already wrote it.
4. Let the tmux session exit normally.

The final screen is best effort. A program that restores the alternate screen
before returning may leave a sparse capture; the transcript remains available.

Add a mode marker in the job state directory. The marker, not command text,
decides TUI behavior for tail, list, and cleanup.

## `mule tail` contract

Ordinary jobs are unchanged.

For a TUI job:

- While running, `mule tail <id>` returns the visible screen from
  `tmux capture-pane -p -J`. This is bounded by pane dimensions and contains
  readable text rather than a redraw stream.
- After exit, `mule tail <id>` returns the `screen` artifact.
- `mule tail --transcript <id>` reads the durable raw transcript. Existing
  selection flags apply to the transcript: default last 64KB, `-n`, or `--all`.
- `mule tail -f <id>` refuses and names murmur jump. Streaming TUI redraw bytes
  is not a useful log-follow contract.
- `--transcript` conflicts with `-f`.

If a running pane disappears before screen capture, return the saved `screen`
when present, otherwise an empty snapshot plus an stderr diagnosis. Do not fall
back silently to raw transcript bytes.

## murmur glance and jump command rendering

### Server-aware glance

Glance uses the server tag already carried in `PaneView`:

```text
default -> tmux capture-pane ...
label   -> tmux -L <label> capture-pane ...
path    -> tmux -S <path> capture-pane ...
```

Use argument arrays for tmux selectors. The remote login shell receives one
shell-quoted command assembled from validated snapshot fields. A glance failure
returns no preview as today; it never deletes state.

### Read-only jump command CLI

Add:

```sh
murmur jump-command --host dev --agent mule-3fa921
```

`--host` resolves an exact peer name first, then a unique exact peer target.
This matters because mule knows its configured SSH target, not murmur's
operator-chosen peer name. Multiple peers with the same target are ambiguous
and fail with the candidates; never pick one by ordering.

The command reads the cached snapshot and peer jump template. It prints exactly
one rendered command on stdout and no decoration:

```sh
x2ssh -et dev -c 'tmux -L mule attach -t %34'
```

It never opens a network connection. Resolve by exact peer name and exact
`agent_name`, including orchestrated rows hidden by the default picker. Missing
or ambiguous matches fail with exit 2 and list the candidate host, agent name,
and pane.

`--json` returns host, agent, pane, server, and command for programmatic callers.
The text form is safe for command substitution:

```sh
attach=$(murmur jump-command --host dev --agent mule-3fa921)
```

Update `murmur --help`, `murmur jump-command --help`, and the private-server
migration error to point at this renderer where a caller needs the exact
command.

## mu control

mule does not create a mu agent row. Crew metadata affects murmur classification
only.

To send keys, read pane output, or wait on agent status through mu, create a
local attach pane:

```sh
mu agent spawn mule-3fa921 --command \
  "$(murmur jump-command --host dev --agent mule-3fa921)"
```

The local pane is the process mu controls. The remote pi remains in mule's
private server. Closing the local mu pane detaches; it does not stop the mule
job. `mule kill --rm <id>` remains the lifecycle command.

mule's post-dispatch hint includes this exact command. If `MU_WORKSTREAM` was
forwarded, include `-w <workstream>` with shell-safe local quoting. Otherwise
omit `-w` and let normal mu resolution apply.

## Safety and compatibility

- Ordinary mule jobs keep the existing log pipeline and behavior.
- `--tui` is explicit. No command-content heuristic enables it.
- `--human` and crew metadata are independent of TUI mode.
- `--max-secs` watchdog, `kill`, `kill --rm`, prune, runtime tracking, and rc
  semantics remain unchanged.
- TUI transcript data is untrusted terminal output. Never replay it to a
  terminal by default; `--transcript` writes raw bytes only because the caller
  asked for them.
- User-controlled command, cwd, and workstream values retain their current
  encoded boundary. `pipe-pane` receives only validated job id, validated tmux
  socket, and typed byte cap.
- murmur remains transport-free in `jump-command`; it renders cached data only.

## CLI hints

Hints are stderr only, suppressed by mule `--quiet` except correctness warnings.
Every command includes the real job id and the shell-quoted configured SSH
target. Do not assume the mule host name equals murmur's peer name, and do not
print placeholders after dispatch.

For `run --tui`, print screen, picker, mu-control, and kill commands. For
`tail -f` refusal, print screen and picker commands. For a missing murmur binary,
mule does not probe or branch; the command may fail normally when pasted.

murmur picker rows need no new prose. `jump-command` help explains that the
result is suitable for `mu agent spawn --command`.

## Tests

### mule

- generated TUI wrapper runs `[ -t 0 ] && [ -t 1 ] && [ -t 2 ]`
- start barrier prevents output loss before `pipe-pane`
- running tail returns a clean screen snapshot
- completed tail returns saved screen
- transcript default, `-n`, `--all`, truncation marker, and hostile terminal
  bytes remain raw and bounded
- `tail -f` refuses only for TUI jobs with pasteable hints
- ordinary job byte logs are unchanged
- `--tui` conflicts with `--wait` and `--no-tail`; `--human` remains valid
- kill, timeout rc 124, explicit kill rc 137, runtime, prune, and cleanup leave
  no session, pipe, FIFO, or state residue
- real local sshd test sends keys into the private pane and observes screen plus
  transcript artifacts

### murmur

- glance renders default, label, and path selectors with hostile values inert
- private-server glance captures a real `tmux -L test-* -f /dev/null` pane
- `jump-command` text stdout is exactly one command; stderr is empty
- JSON shape is stable
- exact agent resolution includes hidden orchestrated agents
- host resolution prefers exact peer name, then unique exact target
- missing and ambiguous host/agent errors list candidates and open no network
- rendered command executes against a fake transport and records literal tmux
  argv

### Cross-repo operator smoke

On `dev`, with live masters and released/local builds:

1. launch real `pi-meta` with `mule run --tui --max-secs 180`
2. assert murmur counts it as crew on server label `mule`
3. assert `mule tail` and murmur glance show readable TUI text
4. render `murmur jump-command`, attach, and send a harmless key/input
5. create a mu attach pane and verify `mu agent read` sees the TUI
6. `mule kill --rm` and assert job, private session, murmur row, local attach,
   pipe consumer, and artifacts are gone

The smoke test is operator-driven and never part of offline default suites.

## Out of scope

- Making every mule job interactive
- Parsing or sanitizing ANSI transcript bytes
- Replaying a transcript as a terminal session
- Having mule discover murmur peer transport configuration
- Having murmur or mu own mule job lifecycle
- Replacing the detached-remote-tmux recipe for agents that do not need mule
  artifacts or runtime controls

## Implementation order
