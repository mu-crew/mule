# Carrying a mu remote worker: lease, forward, exec

Status: proposed, revised after review (see [Review](#review-2026-10-28))
Date: 2026-10-28
Pairs with: [mu/docs/specs/2026-10-28-lease-transport.md](../../../mu/docs/specs/2026-10-28-lease-transport.md)
Amends: [2026-09-15-tui-jobs.md](2026-09-15-tui-jobs.md) (§ mu control, § Out of scope) and [SPEC.md](../../SPEC.md) (§ Contention, § Rejected alternatives)

## Problem

mu runs a remote worker as a local pane whose death is the agent's death.
Today that pane is a held `ssh -t host pi`. On a `MaxSessions 1` host, that
is exactly the long session hold mule exists to remove. Measured 2026-10-28:
while a mu worker ran on `dev`, every other `ssh dev` was refused.

The TUI-jobs spec gave mu an attach pane for a mule job, but it kept
lifecycle with mule ("closing the local mu pane detaches"). That is right
for an operator glancing at a job and wrong for a mu worker: mu removes the
worker's git worktree only after proving nothing runs in it.

mu needs a local process (a **lease**) that:

1. names its job before the job exists, so the job can always be stopped;
2. starts the remote agent as a detached mule job, with no held session;
3. keeps mu's unix control-socket forward bound and verified for the job's
   life;
4. lives exactly as long as the job: it exits when the job ends, and ends
   the job when it is told to exit.

That process is `mule run --lease`. Two supporting verbs make the rest of a
mu profile mule-backed: `mule forward` and `mule exec`. The stop template is
`mule rm <id>`, made a **proof** of stop (§ `mule rm <id>` as a stop, below).

## Forwards: what was measured

Measured on macOS OpenSSH_10.3p1, against the devvm and a loopback `sshd
MaxSessions 1` built from SPEC § Reproduce the channel cap locally.

| Action | Result |
| --- | --- |
| `ssh -S m -L L:R host true` exits | `L` is still held by the master pid (`lsof`); traffic flows |
| `rm L`, then `-O forward -L L:R` | exit **0**, no file. The master still has the forward in its table, so nothing rebinds |
| `-O cancel -L L:R` of a forward that is gone | prints `port not found` and still exits **0** |
| `-O cancel` of a live forward | closes the listener and **leaves the file** (stale, `ECONNREFUSED`) |
| Client-side `-o StreamLocalBindUnlink=yes` on `-O forward` | ignored: the master's own setting governs. Over a stale file, a master started **without** it fails the forward (255); a master started **with** it rebinds (0) |
| Forward, `-O forward`, `-O cancel` while the only session is held | all succeed. Three concurrent forwarded connections also succeed. A forward is a `direct-streamlocal` channel, not a session |
| A forward whose REMOTE does not exist yet | `-O forward` succeeds; `connect(L)` **succeeds** and reads EOF. Once the remote listener starts, the same forward carries traffic. REMOTE is resolved per connection |
| `connect(L)` on a stale file (master gone or forward cancelled) | `ECONNREFUSED` |
| The master exits (`-O exit`, TERM or KILL) | `L` is left behind; `connect` gives `ECONNREFUSED` |
| **Wedge:** forward `L:R`, then `L:R2` (same LOCAL, different REMOTE), then cancel one | both listeners close, but the master's table still lists one. From then on, `cancel L:R` says `port not found` (exit 0) and `forward L:R` exits 0 and binds nothing. Only a master restart recovers. A naive cancel → unlink → forward sequence reproduces it when REMOTE changes for one LOCAL |

Four conclusions follow:

- An exit code from `-O forward` or `-O cancel` proves nothing.
- File existence proves nothing.
- `connect(L)` succeeding proves a live listener, even before the remote
  side exists.
- One LOCAL must never be forwarded to two REMOTEs.

## `mule forward` / `mule unforward`

```text
mule forward   [--host H] --unix LOCAL:REMOTE ...
mule unforward [--host H] --unix LOCAL:REMOTE ...
```

Unix sockets only. These are control-sized channels (a ctl socket, RPC)
riding mule's connection. TCP is out of scope: a dev-server or bulk forward
would share the connection's channel windows with every probe, which is the
"lend mule's connection to transfer tools" alternative SPEC rejects.

**Forward record.** mule writes `~/.local/state/mule/forwards/<host>/<hash of
LOCAL>` holding `LOCAL`, `REMOTE`, the master pid (from `-O check`'s
`pid=N`), and LOCAL's dev+inode after binding. This is forward state for the
master mule owns, not a job index: it is what makes the wedge avoidable,
since OpenSSH has no `-O list`.

`forward`, for each spec:

1. If a record for LOCAL names a **different** REMOTE and the same master
   pid, `-O cancel` that recorded spec first.
2. `-O cancel -L LOCAL:REMOTE`, ignoring its exit.
3. Unlink LOCAL if it is a socket; refuse with exit 1 if it is anything
   else.
4. `-O forward -L LOCAL:REMOTE`.
5. **Verify:** `connect(LOCAL)` succeeds. It need not exchange data, and the
   remote side need not exist.
6. Write the record.

If verify fails after this sequence, the master's table is wedged. Exit 3,
the hand-back code, with `forward table for H is wedged; a human must
restart the master: ssh -O exit …; ssh -MNf …`. That needs the same human
act as a missing master, and a caller must treat it the same way. Any other
failure cancels the forwards this call added and exits 1, naming the first.

`unforward`: `-O cancel`, unlink LOCAL, and delete the record. Idempotent.

**Locking.** Neither verb takes the ticket lock. `-O forward`, `-O cancel`
and `-O check` are handled in the master's mux loop and open no session
(measured above, during a held session). This is made structural with
`Transport::mux_op(host, MuxOp)`, where `MuxOp` is a closed enum
(`Check`, `ForwardUnix(L, R)`, `CancelUnix(L, R)`) with no free-form args
and no `-R`. A remote forward needs a server round trip and must stay
inside the lock. `Fake` records `mux_op` calls.

**Master command.** `master_command` (errors.rs) gains `-o
StreamLocalBindUnlink=yes`. A master started that way rebinds over a stale
file. Masters opened by hand without it still work, because step 3 unlinks.

## `mule run --lease`

```text
mule run --lease [--host H] [--cwd D] [--human] [--max-secs S]
         --job-file F [--forward-unix LOCAL:REMOTE ...] -- <cmd>
```

`--lease` implies `--tui`, requires `--job-file`, and conflicts with
`--wait`/`--no-tail`.

### Sequence

1. **Name the job first.** Generate the id. Write it to `F` atomically
   (temp file + rename, mode 0600, one line), then fsync. Then dispatch.
   `run::dispatch` is refactored to take an id. If the write fails, exit 1
   with nothing dispatched. If the lease dies after the write, the stop
   template still works, because `mule rm` of a never-dispatched id is a
   no-op. No window remains in which a job exists and nobody can name it.
2. **Dispatch** the TUI job exactly as `run --tui` does: same wrapper,
   barrier, artifacts and metadata rules. With no master, exit 3. This is
   the lease's only startup exit 3.
3. **Forward** each spec with `mule forward`. It does not wait for REMOTE
   to exist: the forward is resolved per connection, and mu's ctl handshake
   already retries `refused` until its budget runs out. Each early probe mu
   makes before pi binds its socket costs one `open failed` line in the
   master's log, which is acceptable.
4. **Hold.** Loop on one probe per tick. The probe is the existing poll
   shape, and while the screen is being mirrored (step 5) it also carries
   `capture-pane`, so it is still one locked call. The interval is 1 s,
   backing off to 5 s and resetting on change. Each tick:
   - Job done (`rc` present): print the final screen, unforward, and exit
     with the job's code.
   - Orphan: unforward, exit 5. Missing: unforward, exit 1.
   - Master gone (`-O check` fails), or the connection dropped mid-probe:
     **do not exit.** Print once `master for H is gone; a human must run:
     ssh -MNf …`, then keep checking at 5 s. Exiting would tell mu the agent
     died while it still runs.
   - Forward drift: LOCAL is missing, its dev+inode differ from the record,
     or the master pid differs (a replaced master has none of the old
     forwards). Re-run `forward`. Both checks are local stat and `-O
     check`, so they cost no channel. A wedge seen here prints the hand-back
     line and keeps holding; it does not exit.
5. **Screen.** A status line shows the job id, host, state and forwards, the
   literal attach command (`murmur pick --all  # select <agent>`, as
   `tui_hints` prints today, without executing murmur) and the stop command.
   The remote screen is mirrored into the pane until 30 s after the first
   successful forward, then only on a state change and at exit. That gives
   mu's startup health scan and `mu agent read` real text without paying a
   capture every tick for hours. Stdin is not forwarded.
6. **Signals** (SIGHUP, SIGTERM, SIGINT):
   - The handler only sets a flag, through `signal-hook` or a self-pipe.
     The hold-loop sleep is interruptible.
   - **The pane's tty is gone after SIGHUP.** Rust's `print!`/`eprint!`
     panic on EIO, so the first thing the signal path does is `dup2`
     `/dev/null` onto fds 1 and 2. All later lease output is fallible and
     ignored.
   - Spawn the detached cleanup child (§ Detached cleanup): this mule, this
     config, `rm <id>`. It queues on the ticket lock like any caller, and a
     dead lease's ticket is skipped, as already handled in `wait_for_turn`. Then run `unforward` (a
     lock-free `mux_op`) and exit 129, 143 or 130 at once.
   - The lease never blocks its own exit on the lock: a holder whose ssh
     fell back to a direct connect can keep the ticket for a TCP timeout.
     The stop happens anyway, in the child. mu's stop template is the
     backstop if the child dies too.
   - An in-flight probe whose ssh child also got SIGHUP is abandoned, and
     its ticket is released by pid death.
7. **SIGKILL** cannot be handled. The job keeps running, the forward stays
   in the master, and `F` names the job. mu's stop template ends the job.
   The next `forward` of the same LOCAL cancels the stale listener first.

### Exit codes and cost

**Exit codes:**
- the job's own code when it ends;
- 1 when the job is missing;
- 3 only at startup (no master);
- 5 when the job is an orphan;
- 129, 130 or 143 after a signal.

These overlap with the job's own codes. mu reads none of them: it reads
only pane liveness.

**Cost per lease:** one locked call per tick, 1 s settling to 5 s, plus a
capture folded into the same call during startup. Four leases at 5 s are
0.8 calls/s, roughly 3–8 % channel occupancy at 30–100 ms each. That is
fair through the ticket lock and bounded.

## `mule rm <id>` as a stop

mu deletes its job handle and removes a worktree only after the stop template
exits 0, so exit 0 must mean "this job is not running and its state is gone".
Today `remove(Target::One)` ignores `kill-session` failures and ends with an
unconditional `exit 0`, even when `rm -rf` fails.

New contract for `rm <id>` (the bulk `rm --all` is unchanged):

- Missing job (no state dir, no session): exit 0. Idempotent.
- Otherwise kill `mule-<id>` and `watch-<id>`, then **verify** neither session
  exists (`tmux has-session` fails) and the state dir is gone after `rm -rf`.
  Both hold: exit 0. Either fails: exit 1 naming which, and keep whatever
  evidence is left (a surviving session is not killed again silently; the dir
  is not half-removed by a second pass).
- One round trip, unchanged.

Tested through the real wrapper (layer 2) and the local sshd (layer 3),
including a forced failure (an unremovable file in the state dir; a session
that survives `kill-session` via a mock tmux on PATH).

## Detached cleanup

Both `exec` and the lease stop their job from a signal path by spawning a
detached child. The child must be **this** mule with **this** config:

- Executable: `std::env::current_exe()`, never `mule` from PATH (a worker or
  test runs a freshly built binary; PATH may hold another or none).
- Arguments: the effective `--config` path when one was given (never let the
  child fall back to, or seed, the default config), `--quiet`, `--host H`,
  `rm <id>`.
- Detach portably: `pre_exec` with `setsid()` (via `libc`), stdin/stdout/stderr
  to `/dev/null`. macOS ships no `setsid` executable, so never shell out to it.
- The child queues on the ticket lock like any caller; a dead parent's ticket
  is skipped by `wait_for_turn`.

## `mule exec`

```text
mule exec [--host H] [--cwd D] [--max-secs S] -- <cmd>
```

This gives `ssh host cmd` semantics over mule's private connection, for a
caller that needs a synchronous command and must not hold the default
master. mu's `--exec` template is the motivating caller: a remote `git
worktree add` is budgeted at 120 s, which would be 120 s of murmur refusals
on a capped host.

- **Separate streams.** exec uses its own wrapper mode, which writes stdout
  to `$d/log` and stderr to `$d/err`. After the job ends, exec prints the
  log to stdout and then the err file to stderr. Callers parse stdout and
  read "why" from stderr's first line (mu does both). SPEC § Split stdout
  and stderr rejects two logs **for the job artifact**. exec is a
  synchronous ssh stand-in, not an artifact reader, so the amendment
  applies to exec only.
- **Quiet stderr.** No id line and no hints. mule's non-fatal diagnostics
  (lock-wait notices, `max_running`, dispatch-pattern warnings) are
  suppressed. Only the command's stderr and mule's fatal errors reach
  stderr.
- **Fast poll.** The interval starts at 100 ms and is capped at 1 s, not
  5 s, because the caller is blocked on it.
- **Exit status.** exec exits with the job's code and removes the job.
  - If the log hit `max_log_bytes`, it exits **7** (a new code: output
    truncated) instead of the job's code, so a stdout parser never mistakes
    partial output for complete.
  - exec is for control-sized output. A full log is one locked read.
  - No master: exit 3, unchanged.
- **On SIGINT/SIGTERM** exec spawns the detached cleanup child (§ Detached
  cleanup), as the lease does, and exits. It is best effort, and only real if the caller gives it
  a moment. mu raises its template grace to 5 s for this. That is the
  difference from `run --wait`, where the job continues.
- **Cost:** about 125 ms to dispatch plus at least 100 ms of polling,
  against 33 ms for a bare ssh. mu's exec calls are a handful per spawn and
  close. The sub-second ones become jobs too, because a profile has one
  `exec` template, and a refused `git rev-parse` reads as an empty answer
  (SPEC § What belongs in a job).

## Amendments

### SPEC.md

- **§ Contention:** "Every SSH call takes the per-host ticket lock except
  `ssh -O check`" becomes "except the mux ops `-O check`, `-O forward` and
  `-O cancel` for **local unix** forwards". Each opens no session and is
  handled in the master's mux loop, measured during a held session. `-R` is
  excluded, because it needs a server round trip.
- **New § Leases:** a lease is a per-job foreground waiter, like `run
  --wait`.
  - It holds a forward listener, which is not a session.
  - It re-arms forwards after drift.
  - It never re-dispatches, retries, queues or places a job.
  - Every ssh call it makes is sub-second.
  The carve-out from § Add a local scheduler or supervisor covers idempotent
  forward repair only. It cross-references that section.
- **§ Rejected alternatives, Lend mule's connection:** add that unix
  control-socket forwards are the one exemption, because they carry
  control-sized traffic. TCP and bulk forwards stay rejected.
- **§ Store a local job index:** add that a forward record is not a job
  index. It exists only because OpenSSH cannot list a master's forwards.

### TUI-jobs spec

- **§ mu control:** "mule does not create a mu agent row" stands. Add that
  mu may own a mule job's **lifecycle** through the user's stop template
  (`mule rm {job}`): mule still does the work, and mu only decides when.
- **§ Out of scope,** "Having murmur or mu own mule job lifecycle": narrowed
  to the job's mechanics.
- The attach-pane recipe stays for operator viewing. mu workers use a lease.

## Tests

### Layer 1 (fake transport)

- The lease writes `F` before dispatch. A write failure dispatches nothing.
- Each terminal state maps to its exit and unforward. A missing master
  neither exits nor stops the job. Drift (missing file, new inode, new
  master pid) re-forwards.
- Signal path: the fds are redirected first, then the detached `rm` child
  is spawned, then unforward, then exit. No panic on a closed stdout.
- `forward`:
  - cancels a recorded different-REMOTE spec first;
  - runs cancel → unlink → forward → connect-verify;
  - a failed verify exits 3 with the wedge message;
  - refuses a non-socket LOCAL.
- `mux_op` is the only lock-free path, and four concurrent `run` callers
  still never overlap (the existing observation test).
- `exec`:
  - stdout is the log only and stderr is the err file only, with no id and
    no hints;
  - a truncated log exits 7;
  - the job is removed afterwards;
  - polling never exceeds 1 s.
- A multi-word `--lease` command with `env K=v sh -c '…'` reaches the remote
  shell with its env applied.

### Layer 3 (local `sshd MaxSessions 1`)

- Lease plus forward of a socket the job serves: traffic flows, and `ssh -S
  <other master> host true` succeeds during the hold.
- `rm LOCAL` while leased: the next tick re-forwards.
- `-O exit` of mule's master, then reopening it: the lease prints the
  hand-back line, stays up, and re-forwards on the new pid.
- `tmux kill-pane` mid-print and mid-probe: the job's session and state dir
  are eventually gone (`rm` removes the dir, so no `rc` is left to read), the
  forward is cancelled, the file is gone, and there is no panic.
- `kill -9` the lease: the job survives. A new lease's `forward` of the
  same LOCAL succeeds, and `mule rm <id from F>` ends the job.
- The wedge sequence (`L:R`, `L:R2`, cancel) is avoided through the record,
  and when forced by hand, it is detected as exit 3.
- `exec` of a 30 s command: a concurrent default-master ssh succeeds.

## Size

About 350 LOC:
- `lease.rs`: the hold loop, signals, screen.
- `forward.rs`: the verbs and the record.
- `exec` wrapper mode and verb.
- `mux_op`.
- the `dispatch` id refactor.

Tests come on top. One dependency, `signal-hook`, unless a self-pipe over
the existing `libc` usage is preferred.

## Out of scope

- TCP forwards, and moving `t3-dev` onto `mule forward`. `t3-dev`'s HTTP
  forward is not control-sized.
- Forwarding keystrokes from the lease pane into the remote TUI. That would
  be a held stream.
- Opening or restarting the master. A missing or wedged master is exit 3,
  or the lease's waiting line.
- Re-dispatching after an orphan.

## Review (2026-10-28)

The first draft was reviewed against the code and SPEC, and its claims were
re-measured on a loopback capped sshd. Accepted and folded in:

- The id is written before dispatch. The first draft wrote it after, which
  left an unnameable job.
- The signal path survives a hung-up tty and never blocks on the ticket
  lock: a detached `rm` child.
- `kill --missing-ok` was dropped: `mule rm <id>` is the stop. A plan review
  then found `rm` exits 0 even when the kill or removal fails; § `mule rm <id>`
  as a stop makes exit 0 a proof. The same review found the detached cleanup
  would lose a private `--config` and that macOS has no `setsid` executable:
  § Detached cleanup.
- exec separates streams, silences mule's stderr, polls fast, and exits 7
  on truncation.
- `--tcp` and the `t3-dev` migration were dropped.
- Verify moved from file existence to `connect()`, with drift detection by
  inode and master pid. The forward record and wedge detection are new;
  the wedge was found by the measurement refuter.
- The wait for REMOTE was removed: forwarding does not need it.
- Client-side `StreamLocalBindUnlink` is ignored, so it is now set on the
  master command.
- Screen mirroring was folded into the probe and time-limited. The cost
  sentence was corrected.
- Exit-code wording fixed. The murmur command is printed, not executed.
- SPEC amendments are written out instead of resting on an analogy.
